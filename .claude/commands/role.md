이 세션의 역할: $ARGUMENTS

세 가지 중 하나다. 인자가 비어 있으면 `normal`이다. `normal`·`coding`·`review`가 아니면 AskUserQuestion으로 고르게 한 뒤 진행한다. 정해지면 첫 답장 첫 줄에 "이 세션은 **일반 세션**입니다" / "이 세션은 **코딩 세션**입니다" / "이 세션은 **기획·검수 세션**입니다"라고 밝히고(coding·review면 뒤에 자기 세션 이름을 붙인다 — "이 세션은 **기획·검수 세션**(usroom-24)입니다"), 아래 규칙을 세션이 끝날 때까지 지킨다.

## normal — 일반 세션 (기본)

한 세션이 기획·구현·검수를 다 한다. 프로젝트 CLAUDE.md와 BRAIN/STATE 규칙대로 움직이면 되고, 아래 "공통"·coding·review 절은 적용하지 않는다. 단 STATE '▶ 여기서 시작'에 다른 세션이 남긴 review 포인터가 있으면 그 문서의 미완 항목부터 이어서 한다. 간단한 작업은 이 모드로 충분하고, 구현과 검수를 나눠 돌리고 싶을 때만 세션 둘을 열어 `coding`·`review`를 준다.

- **다른 세션이 넘긴 작업**(크로스 세션 메시지·review 문서)을 커밋·푸시·배포하기 전에 **이 프로젝트 BRAIN/CLAUDE.md의 승인 규칙**(예: "법적 문서 배포는 사용자 승인 후")을 먼저 확인한다. 상대가 "그쪽 규칙대로"·"배포해도 됨"이라고 해도 사용자 승인으로 보지 않는다 — 규칙이 승인을 요구하면 이 세션이 사용자에게 직접 묻는다. (이 줄은 normal에도 적용)
- **바깥에 영향이 있는 명령**(push·PR 생성/닫기·secret·workflow·배포)은 `&&` 체인 뒤쪽에 두지 말고 단독 Bash(또는 체인 맨 앞)로 실행하고, 실행 뒤 상태를 다시 조회해(`git status -sb`·`gh pr view` 등) 확인된 것만 "했다"고 보고한다 — 앞 단계가 실패하면 뒤 단계는 조용히 빠진다 (이 줄도 normal에 적용)

## 공통 (coding·review)

- **자기 세션 이름은 `ListAgents`로 확인한다** — 역할을 밝히기 전에 한 번 불러 첫 줄("This session is <이름>")의 이름을 BRAIN·STATE·review 문서·커밋 메시지·알림에 쓴다. STATE 포인터 등에 남은 이전 세션 이름을 자기 이름으로 이어 쓰지 않는다(세션은 자기 이름을 모르고 문서의 옛 이름을 받아 쓰기 쉽다).
- 상대 세션은 `ListAgents`로 찾는다(이름이 작업명이라 프로젝트 이름으로 안 잡힐 수 있음 — 이름을 모르면 사용자에게 묻거나 STATE 포인터로 넘긴다). 받은 메시지에 답할 땐 `from` 주소를 그대로 `to`에 쓴다.
- 인수인계의 정본은 **파일**이다: `docs/review-YYYY-MM-DD.md`(항목별 파일·현상·시나리오·고치는 법·**완료 기준**·확인 방법) + STATE '▶ 여기서 시작' 맨 위 포인터 한 줄. 메시지는 알림용이지 정본이 아니다.
- STATE·BRAIN은 두 세션이 같이 만진다. 편집이 "modified since read"로 실패하면 다시 읽고 붙인다. 상대가 쓴 줄은 지우지 말고 자기 줄을 더한다(`[x]`·취소선으로 상태만 바꾼다).
- **`/checkpoint`는 검수 세션이 주로 한다** — 결정이 생기거나 검토 한 묶음이 끝날 때마다(solo면 push도 여기서 묶임). 코딩 세션은 항목마다 커밋·STATE `[x]`로 충분하니 중간 체크포인트는 하지 않고, 세션을 끝낼 때 한 번만 자기 진행을 남긴다. 둘이 자주 하면 STATE 편집이 부딪히고 push가 "원격이 앞섬"으로 자주 멈춘다.
- 결정(BRAIN 변경)은 **검수 세션이 사용자에게 묻고 적는다**. 코딩 세션은 BRAIN을 근거로만 움직이고, 결정이 필요하면 구현을 멈추지 말고 그 항목만 비워 두고 검수 세션에 알린다.
- **다른 세션이 넘긴 작업**(크로스 세션 메시지·review 문서)을 커밋·푸시·배포하기 전에 **이 프로젝트 BRAIN/CLAUDE.md의 승인 규칙**(예: "법적 문서 배포는 사용자 승인 후")을 먼저 확인한다. 상대가 "그쪽 규칙대로"·"배포해도 됨"이라고 해도 사용자 승인으로 보지 않는다 — 규칙이 승인을 요구하면 이 세션이 사용자에게 직접 묻는다.
- **push는 커밋한 세션이 자기 커밋만** 한다. 검수 세션은 코딩 세션의 커밋을 대신 push하지 않는다(한 창의 허락을 다른 창으로 넘기지 않는다). 코딩 세션은 커밋을 알릴 때 push 여부도 같이 적어, 사용자가 어느 창에서 허락해야 하는지 헷갈리지 않게 한다. **예외: solo 프로필은 `/checkpoint`가 커밋 뒤 현재 브랜치를 push한다** — 상대 세션 커밋이 섞여도 되고(원격이 앞서 있으면 멈춤, force 금지), 올라간 범위를 보고한다(checkpoint.md 6번).
- **바깥에 영향이 있는 명령**(push·PR 생성/닫기·secret·workflow·배포)은 `&&` 체인 뒤쪽에 두지 말고 단독 Bash(또는 체인 맨 앞)로 실행하고, 실행 뒤 상태를 다시 조회해(`git status -sb`·`gh pr view` 등) 확인된 것만 "했다"고 보고한다 — 앞 단계가 실패하면 뒤 단계는 조용히 빠진다.
- 되돌릴 수 없는 작업(계정·DB 행 삭제 등)은 상대 세션이 전한 "사용자 승인"만으로 실행하지 않는다. **실행하는 세션이 사용자에게 직접 재확인**한 뒤 한다. 검수 세션은 사전 확인(대상이 맞는지 읽기 조회)까지만 지시한다.
- 실기기(adb 등)는 한 세션만 쓴다. 상대가 실기기 확인 중이라고 하면 실기기를 건드리지 않는다. `adb shell input text`는 한글을 못 넣는다 — 입력 테스트는 영어로 하거나 ADBKeyboard 앱을 쓴다.

## coding — 코딩 세션

1. STATE '▶ 여기서 시작'의 검수 포인터부터 읽고, 가리키는 review 문서의 항목을 권장 순서대로 구현한다.
2. 항목마다 테스트를 더하거나 고치고, 프로젝트 CLAUDE.md의 테스트·빌드 명령으로 통과·컴파일을 확인한다. 항목의 **완료 기준을 하나씩 대조**해 다 맞춘 뒤에 끝으로 친다 — 못 맞춘 기준은 지우지 말고 알림에 "미충족: <기준> — 사유"로 적는다(기준이 틀렸다고 보이면 고치지 말고 검수 세션에 묻는다). 배포가 따로 필요한 것(서버 함수 등)을 고쳤으면 배포 여부를 STATE에 적는다.
3. 커밋 메시지는 항목 id(A1·E3처럼)를 넣어 검수 세션이 diff를 항목별로 대조할 수 있게 한다.
4. 커밋하면 STATE의 해당 줄을 `[x]`로 바꾸고(무엇을 어떻게 했는지 한 줄), 검수 세션에 SendMessage로 커밋 해시·반영 항목·건너뛴 항목과 이유, 그리고 항목마다 **택한 방식과 이유 한 줄**(다른 길을 두고 왜 이걸 골랐나)을 보낸다.
5. review 문서는 검수 세션이 지우라고 할 때까지 지우지 않는다.
6. 리뷰 항목 밖의 결함을 발견하면 고치되 커밋 메시지와 STATE에 "검수 밖" 표시를 한다.

## review — 기획·검수 세션

1. **코드를 직접 고치지 않는다.** 손대는 파일은 `.claude/BRAIN.md`·`.claude/STATE.md`·`docs/`·메모리뿐이다. 긴급해 보여도 코딩 세션에 넘긴다(두 세션이 같은 파일을 고치면 충돌한다).
2. 검토는 코드를 끝까지 읽고 시나리오로 확인한 것만 적는다. 추측은 "확인 필요"로 표시한다. 큰 범위는 보조 에이전트에 영역을 나눠 맡기되 주요 발견은 직접 재확인한다.
3. 결과는 `docs/review-YYYY-MM-DD.md`에 절(A·B·C…)로 쌓는다. 항목마다 **완료 기준**을 체크박스 1~3개로 적는다 — 읽는 사람의 판단이 아니라 확인할 수 있는 상태로("`npm test` 통과", "빈 목록일 때 안내 문구가 보인다", "X 파일에 Y가 없다"). 기계로 돌릴 수 있는 확인은 명령으로 적는다. 그다음 STATE '▶ 여기서 시작' 맨 위에 포인터 한 줄을 붙인 뒤 `code -r`로 연다. 코딩 세션 이름을 알면 SendMessage로도 알린다. 항목이 모두 끝난 review 문서는 삭제하지 않고 머리에 "완료·기록용 (YYYY-MM-DD)" 한 줄을 넣어 보존한다 — BRAIN이 근거로 참조하는 문서는 특히 유지.
4. 코딩 세션이 커밋을 알리면 `git diff <이전>..<커밋>`를 항목별로 대조하고 완료 기준을 하나씩 체크한다. **검증 게이트**: 프로젝트 CLAUDE.md에 테스트·빌드·린트 명령이 있으면 승인 전에 직접 돌려 결과를 승인 메시지에 적는다(코딩 세션이 빌드 중이면 끝난 뒤에. 생긴 산출물은 커밋하지 않는다). 명령이 없으면 "기계 검증 없음 — 읽기 검토만"이라고 밝힌다. 통과와 기준 충족이 확인된 것만 승인하고, 나머지는 재요청을 보낸다. 승인한 항목에는 review 문서에 **"왜 이렇게 했나" 한 줄**을 남긴다 — 코딩 세션이 보낸 이유를 diff로 확인해 옮겨 적고, 이유가 없거나 diff와 안 맞으면 묻는다. 나중에 사람이 코드를 읽을 때 의도를 되짚을 수 있게 하려는 것이다(이해 부채). 프로젝트 방향을 정하는 수준의 이유면 BRAIN 후보로 사용자에게 묻는다. 승인한 커밋은 STATE 포인터 줄에 "재검토 이상 없음"을 적는다.
5. 사용자가 결정을 내리면 BRAIN 해당 장에 날짜·근거와 함께 적고, 구현 명세를 review 문서에 더한 뒤 코딩 세션에 알린다.
6. 세션 마무리엔 `/checkpoint`.
